Core Concepts Demystified

Spring feels like magic because it hides plain Java behind annotations. Here is what is really going on.

Dependency Injection (IoC) CORE
Analogy: A restaurant chef does not farm vegetables or build the oven. Suppliers deliver what the kitchen needs and the manager decides which supplier to use. The chef just says, "I need a vegetable supplier." Spring is the manager: your class declares what it needs and Spring hands it over.

Inversion of Control: instead of your code creating its collaborators (new), a container creates and wires them. Dependency Injection is the mechanism: dependencies arrive through the constructor.

java
// WITHOUT DI: tightly coupled, hard to test, hard to swap
class OrderService {
    private final OrderRepository repo = new MySqlOrderRepository(); // hard-wired
}

// WITH DI: depends on an abstraction, Spring supplies the implementation
public interface OrderRepository { Optional<Order> findById(Long id); }

@Repository
class MySqlOrderRepository implements OrderRepository { /* ... */ }

@Service
class OrderService {
    private final OrderRepository repo;

    // Single constructor: @Autowired is optional in Spring 4.3+
    OrderService(OrderRepository repo) { this.repo = repo; }
}

// In a unit test, no Spring needed:
var service = new OrderService(new InMemoryOrderRepository());

Under the hood: at startup Spring scans for @Component-family classes, builds BeanDefinitions, creates the beans in dependency order, and stores them in the ApplicationContext (a map of name/type to singleton). Prefer constructor injection: dependencies are final, required, and testable. Avoid field injection.

Mobile parallel: same idea as Hilt/Dagger on Android or Swinject on iOS.

ORM and Hibernate CORE
Analogy: A translator between two people who speak different languages. Your Java objects speak "objects and references"; the database speaks "tables and foreign keys." Hibernate translates in both directions so you rarely write SQL by hand.

JPA is the specification (interfaces and annotations). Hibernate is the main implementation. Spring Data JPA sits on top and generates repository implementations for you.

java
@Entity
@Table(name = "subscriber")
public class Subscriber {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "msisdn", nullable = false, unique = true, length = 15)
    private String msisdn;

    @Column(name = "full_name", nullable = false)
    private String fullName;

    @Enumerated(EnumType.STRING)   // store "ACTIVE", not 0/1
    private SubscriberStatus status;

    protected Subscriber() {}      // JPA requires a no-arg constructor
}

Which maps to this SQL (what Hibernate generates / expects):

sql
CREATE TABLE subscriber (
    id        BIGINT AUTO_INCREMENT PRIMARY KEY,
    msisdn    VARCHAR(15)  NOT NULL UNIQUE,
    full_name VARCHAR(255) NOT NULL,
    status    VARCHAR(255)
);

-- repo.save(sub)       => INSERT INTO subscriber (...) VALUES (...)
-- repo.findById(1L)    => SELECT ... FROM subscriber WHERE id = 1
-- sub.setFullName("X") inside @Transactional => UPDATE on commit (dirty checking)

Key idea, the persistence context: inside a transaction Hibernate tracks every entity it loaded. If you change a field, it detects the change ("dirty checking") and issues the UPDATE at commit, with no explicit save() needed.

@RestController
@RequestMapping("/api/v1/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @PostMapping
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest req) {
        OrderResponse created = service.create(req);                  // 1. delegate
        return ResponseEntity.status(HttpStatus.CREATED).body(created); // 2. 201
    }
}

@Service
class OrderService {
    private final ServiceOrderRepository repo;
    OrderService(ServiceOrderRepository repo) { this.repo = repo; }

    @Transactional                                   // opens tx, commits or rolls back
    OrderResponse create(CreateOrderRequest req) {
        ServiceOrder order = ServiceOrder.pending(req.subscriberId(), req.serviceCode());
        return OrderResponse.from(repo.save(order)); // INSERT
    }
}

@Transactional gotchas (classic interview material)

java
@Service
class PaymentService {
    @Transactional
    public void outer() {
        inner();   // SELF-INVOCATION: bypasses the proxy, so inner's @Transactional is IGNORED
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void inner() { }
}
// Other traps: private/final methods can't be proxied; the default rolls back only for
// unchecked exceptions (use rollbackFor = Exception.class); a long tx holds a DB connection.

@Entity
class Subscriber {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id;

    private List<ServiceOrder> orders = new ArrayList<>();     // LAZY by default

@Entity
class ServiceOrder {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id;

    @ManyToOne(fetch = FetchType.LAZY)                         // override the EAGER default
    @JoinColumn(name = "subscriber_id", nullable = false)
    private Subscriber subscriber;                             // owns the FK
}

Telecom OMS Project Architecture

A Telecom Order Management System: customers (subscribers) order services (data plans, SIMs, add-ons), and the system tracks each order until the service is live. It's a good portfolio piece because it has real state, transactions, and integration points.

Scope & stack
  • Stack: Java 21, Spring Boot 3.x, Spring Data JPA, PostgreSQL, Flyway, Docker, JUnit 5 + Testcontainers.
  • API: REST + OpenAPI (springdoc). Idempotent order creation via an Idempotency-Key header.
  • Stretch (months 4 to 5): Kafka event on each state change, Redis cache for the catalog, JWT auth, CI with GitHub Actions.

Order State Machine: PENDING → PROVISIONING → ACTIVE
PENDING→ PROVISIONING→ ACTIVE
PENDING→CANCELLED · PROVISIONING→FAILED · ACTIVE→TERMINATED
FromToTrigger
PENDINGPROVISIONINGValidation passed, request sent to the network/provisioning system
PROVISIONINGACTIVEProvisioning callback confirms success
PROVISIONINGFAILEDProvisioning error or timeout (can be retried → PROVISIONING)
PENDINGCANCELLEDCustomer cancels before provisioning starts
ACTIVETERMINATEDCustomer or system ends the service

Put the rules inside the enum, so illegal transitions are impossible by construction:

java
public enum OrderStatus {
    PENDING, PROVISIONING, ACTIVE, FAILED, CANCELLED, TERMINATED;

    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        PENDING,      Set.of(PROVISIONING, CANCELLED),
        PROVISIONING, Set.of(ACTIVE, FAILED),
        FAILED,       Set.of(PROVISIONING),
        ACTIVE,       Set.of(TERMINATED),
        CANCELLED,    Set.of(),
        TERMINATED,   Set.of());

    public boolean canMoveTo(OrderStatus next) { return ALLOWED.get(this).contains(next); }
}

@Entity
public class ServiceOrder {
    @Enumerated(EnumType.STRING) private OrderStatus status = OrderStatus.PENDING;
    @Version private long version;                    // blocks lost updates from concurrent callbacks

    public void transitionTo(OrderStatus next) {
        if (!status.canMoveTo(next))
            throw new IllegalStateException(status + " -> " + next + " is not allowed");
        this.status = next;
    }
}

@Transactional
public void onProvisioningSuccess(Long orderId) {
    ServiceOrder o = repo.findById(orderId).orElseThrow();
    o.transitionTo(OrderStatus.ACTIVE);               // dirty checking issues the UPDATE
}
Senior-level touches: optimistic locking (@Version), idempotent callbacks (a repeated "success" must not fail), an audit table for status history, and an outbox table feeding Kafka events.

Section 5

Senior Engineer Interview Prep

Top 10 Java / Spring Boot questions

1. What is Dependency Injection and why use it?

Objects receive their dependencies instead of creating them. It decouples classes from concrete implementations, which makes code easier to test (swap in mocks) and change. Prefer constructor injection: dependencies are final and required.

2. How does HashMap work internally?

An array of buckets. The key's hashCode() picks a bucket, equals() resolves collisions inside it. Collisions form a linked list that treeifies into a red-black tree at 8 entries (Java 8+). Default load factor 0.75: when exceeded, the table doubles and rehashes. Average O(1), worst case O(log n).

3. == vs equals(), and the hashCode contract?

== compares references; equals() compares logical equality. If two objects are equal they must return the same hashCode(). Break this and HashMap/HashSet misbehave. Records generate both correctly.

4. How does Spring Boot auto-configuration work?

@EnableAutoConfiguration loads candidate configuration classes listed in META-INF/spring/...AutoConfiguration.imports from starters on the classpath. Each is guarded by conditions (@ConditionalOnClass, @ConditionalOnMissingBean), so it only applies when relevant and backs off when you define your own bean.

5. @Component vs @Bean?

@Component (and @Service, @Repository) marks your class for classpath scanning. @Bean is a method in a @Configuration class that returns an object, and is used for third-party classes or when you need custom construction.

6. How does @Transactional work and what are the pitfalls?

A proxy wraps the bean, opens a transaction before the method and commits or rolls back after. Pitfalls: self-invocation bypasses the proxy; only public methods through the proxy are covered; checked exceptions don't roll back by default; a long transaction holds a connection. Know propagation (REQUIRED, REQUIRES_NEW) and isolation basics.

7. What is the N+1 problem and how do you fix it?

One query loads N parents, then lazy access fires one extra query per parent. Fix with JOIN FETCH, @EntityGraph, batch fetching (@BatchSize), or a DTO projection. Detect it by logging SQL in tests.

8. map() vs flatMap() in streams?

map transforms each element 1:1. flatMap maps each element to a stream and flattens the results into one stream (1:N). Same distinction on Optional.

9. HashMap vs ConcurrentHashMap, and thread-safety basics?

HashMap is not thread-safe. ConcurrentHashMap allows safe concurrent access with fine-grained locking/CAS and atomic operations like computeIfAbsent. Know synchronized vs ReentrantLock, volatile (visibility, not atomicity), thread pools via ExecutorService, and that virtual threads (Java 21) suit blocking I/O.

10. PUT vs PATCH vs POST, and what is idempotency?

PUT replaces a resource (idempotent). PATCH partially updates it. POST creates or triggers actions (not idempotent by default). Idempotent means repeating the call has the same effect as once. Make POSTs safe to retry with an idempotency key, which matters a lot for payments and orders.

Also be ready for: JVM memory (heap, stack, metaspace) and garbage collection basics, SOLID, checked vs unchecked exceptions, bean scopes, @Async, DB indexing and isolation levels, and Spring Security/JWT basics.

Caching

  • Cache-aside: read cache first; on a miss read the DB and populate the cache. Most common.
  • Use for read-heavy, rarely-changing data (service catalog). Set a TTL; invalidate on write.
  • Tools: Redis (distributed), Caffeine (in-process). In Spring: @EnableCaching + @Cacheable/@CacheEvict.
  • Hard parts: stale data, cache stampede, and deciding what not to cache.
java
@Cacheable(value = "catalog", key = "#code")
public ServiceCatalog findByCode(String code) { return repo.findByCode(code).orElseThrow(); }

@CacheEvict(value = "catalog", key = "#c.code")
public void update(ServiceCatalog c) { repo.save(c); }

Message queues

  • Why: decouple services, absorb traffic spikes, retry failures, process asynchronously.
  • Kafka: distributed log, high throughput, replayable, partition-ordered. Good for event streams.
  • RabbitMQ: classic broker with routing and acks. Good for task queues.
  • Must know: at-least-once delivery means consumers must be idempotent. Use a dead-letter queue for poison messages, and the outbox pattern to publish events reliably with a DB write.

Other building blocks

  • Load balancer + stateless services (keep session state out of the app).
  • DB: indexes, read replicas, pagination, connection pooling (HikariCP).
  • Resilience: timeouts, retries with backoff, circuit breaker (Resilience4j), rate limiting.
  • Observability: structured logs, metrics (Micrometer/Prometheus), distributed tracing.
Interview framework: clarify requirements → estimate scale → sketch API + data model → draw the high-level design → deep-dive one bottleneck → discuss trade-offs. Say your trade-offs out loud.
Framing your mobile experience as a backend advantage
  • You are the API's customer. You know what a painful API looks like: chatty endpoints, inconsistent errors, no pagination, breaking changes. Say: "I design APIs from the consumer's point of view."
  • Real-world constraints: flaky networks, retries, offline sync, and battery taught you idempotency, timeouts, and graceful degradation, the same topics as resilient backends.
  • Versioning pain: old app versions live for months. That is a first-hand case for backward-compatible changes and API versioning.
  • Payload discipline: you have fought large responses, so you naturally design lean DTOs, pagination, and caching headers (ETag).
  • End-to-end ownership: auth flows (OAuth/JWT), push notifications, crash analytics, and release pipelines are transferable to backend CI/CD and observability.
  • Concurrency mindset: async/await, coroutines, and main-thread rules map directly to thread pools, futures, and non-blocking I/O.
